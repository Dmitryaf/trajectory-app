# Правила проекта `Траектория`

Общие правила подключаются через `RULESET.md` в этой же директории. Здесь находится только устойчивая специфика проекта; текущие задачи, датированные наблюдения и временные beta-приоритеты остаются в своих канонических источниках.

## Назначение

«Траектория» — PWA для коротких личных записей и последующего недельного, месячного и долгосрочного обзора. Продукт помогает сопоставить фактические действия, состояние и контекст, а затем выбрать одно следующее решение без общей оценки человека или дня.

## Неприкосновенные ограничения

- Не терять, не смешивать и не подменять личные данные. Отсутствие, неизвестное значение и незаполненный блок сохраняют разную семантику.
- Сохранять обратную совместимость IndexedDB, JSON-резервных копий и облачных снимков. Изменение данных проходит через schema, нормализацию, store, backup/cloud границы, экспорт, аналитику и профильные тесты в той мере, в которой они затронуты.
- Не выдавать последовательность, совпадение или малую выборку за причинность, диагноз или прогноз. Неполные периоды и число наблюдений остаются видимыми.
- Сохранять ежедневный ввод необязательным и низкозатратным. Новое обязательное поле требует подтверждённой пользы для недельного или месячного решения.
- При обязательной авторизации приложение закрывается безопасным экраном, если backend-конфигурация отсутствует. Привилегированный ключ Supabase не попадает во frontend; облачные строки изолируются через `auth.uid()` и RLS.

## Структура и документация

- [`../docs/README.md`](../docs/README.md) — индекс проектной документации; не читать всю папку `docs/` без связи с задачей.
- [`../docs/agent/WORKFLOW.md`](../docs/agent/WORKFLOW.md) — локальный процесс; читать в начале средней или большой задачи.
- В [`../docs/agent/QUALITY.md`](../docs/agent/QUALITY.md) до реализации читать относящиеся к изменению канонические решения для повторяющихся регрессий, а перед проверками — относящиеся к задаче критерии самопроверки.
- [`../docs/agent/PRODUCT.md`](../docs/agent/PRODUCT.md) — локальные продуктовые и UI-ограничения; читать для продуктовых, текстовых и интерфейсных изменений.
- [`../docs/product/PRODUCT_RULES.md`](../docs/product/PRODUCT_RULES.md) и [`ANALYTICS_DATA_CONTRACT.md`](../docs/product/ANALYTICS_DATA_CONTRACT.md) — канонические продуктовые и аналитические инварианты.
- [`../docs/development/ARCHITECTURE.md`](../docs/development/ARCHITECTURE.md) — границы `src/features`, `src/model`, store, views и общих модулей.
- [`../docs/operations/DATA_GOVERNANCE.md`](../docs/operations/DATA_GOVERNANCE.md), [`BETA_RELEASE.md`](../docs/operations/BETA_RELEASE.md) и [`DELIVERY.md`](../docs/operations/DELIVERY.md) — данные, beta-gate, ветки и выпуск.
- [`../docs/planning/BACKLOG.md`](../docs/planning/BACKLOG.md) хранит стратегию и приоритеты. Текущие исполнимые задачи ведутся в одном GitHub Project; параллельный список мелких задач в документации не создаётся.
- Код развивается вертикальными срезами пользовательских сценариев. Общая абстракция появляется после реальных повторных потребителей, а не для выравнивания структуры каталогов.

## Граница документации

- Репозиторий сейчас приватный. Текущие `docs/agent/`, `docs/planning/`, `docs/audits/`, `docs/OWNER_GUIDE.md` и внутренние operations-документы не считаются готовыми к публикации только потому, что находятся в Git.
- Допустимая публичная граница и процедура очистки описаны в [`../docs/operations/PUBLIC_REPOSITORY.md`](../docs/operations/PUBLIC_REPOSITORY.md). Реальные пользовательские данные, секреты, логи, снимки базы и внутренний контекст не публикуются.
- Публикация документа оправдана, если у него есть внешняя аудитория и практическая цель: понять продукт, безопасно запустить, проверить, использовать или внести изменение. Перед публикацией проверяются текущие файлы, ссылки, личный контекст и история затронутых путей.

## Проверки

- После изменения кода или конфигурации: `npm.cmd run check`, затем `git diff --check` и `git status --short`.
- После изменения пользовательского интерфейса дополнительно выполнить целевой Playwright-сценарий для затронутого пути, состояний и ширин. Если менялись общий каркас приложения, навигация, адаптивные правила, закреплённые элементы или раскладка условных блоков, выполнить полный `npm.cmd run test:e2e`; `npm.cmd run check` не проверяет визуальные отношения сам по себе.
- Если затронуты Clipboard/Download API, маршруты, авторизация или облачная сверка, дополнительно выполнить `npm.cmd run test:e2e`.
- Для изменений только Markdown проверить формат изменённых файлов, ссылки, `git diff --check` и `git status --short`; полный frontend gate не требуется без изменения кода, конфигурации или зависимостей.
- После изменения manifest, lock или состава AI Rules выполнить `ai-rules.ps1 doctor`, `status` и read-only `plan` для этого проекта. Managed-файлы внутри `.ai-rules/upstream/` вручную не редактировать.
- Перед staging и production выполнить полный `npm.cmd run test:e2e` и профильные ручные проверки из `docs/operations/DELIVERY.md` и `docs/operations/BETA_RELEASE.md`; зелёный CI не заменяет эффект, который он не наблюдает.

## Специфичные правила

- Для продуктовой функции до реализации ответить, какое решение пользователя она улучшает, на каком периоде работает, как остаётся необязательной, где появляется в аналитике и какие выводы из неё запрещены.
- Для UI проверять мобильную ширину, клавиатурный ввод, длинные списки и стабильность высоты условных элементов. Основной экран показывает компактную сводку; растущая история остаётся в архиве с поиском, периодом и фильтрами.
- Для аналитики сохранять полноту выборки, особые дни, фактическую границу данных и `n`. Не продолжать график в будущее и не заполнять неизвестное правдоподобным значением.
- Для миграции пользовательского варианта заранее определить судьбу старых записей и защитить выбранное преобразование тестом.
- `develop` является staging, `main` — production. Ветки, PR, merge-стратегия и hotfix-путь определяются только `docs/operations/DELIVERY.md` и не дублируются здесь.

## Не сейчас

- Актуальные отложенные направления и условия возврата находятся только в `docs/planning/BACKLOG.md`. Не копировать сюда текущий backlog, beta-статус, номера задач или датированные решения.
