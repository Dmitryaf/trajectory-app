# Участие в разработке

Спасибо за интерес к «Траектории». Начинайте с небольшого изменения, которое можно проверить отдельно и понять по интерфейсу.

## Быстрый запуск

Нужны Node.js 22 и npm.

```bash
npm ci
npm run dev
```

Перед отправкой изменений выполните:

```bash
npm run check
git diff --check
```

Для первого запуска браузерных тестов установите Chromium:

```bash
npx playwright install chromium
npm run test:e2e
```

## Как найти место изменения

1. Найдите видимый текст, обработчик события или маршрут страницы.
2. Проследите путь от `src/views/` или `src/components/` к сценарию в `src/features/` и состоянию в `src/stores/`.
3. Найдите ближайший тест и сначала зафиксируйте в нём ожидаемое поведение.
4. Для первой задачи выбирайте локальное изменение интерфейса или одного сценария. Не начинайте с модели данных, синхронизации, авторизации или миграции без отдельного плана.

Карта зависимостей и правила разделения кода находятся в [архитектуре](./docs/development/ARCHITECTURE.md). Продуктовые ограничения и осторожные формулировки описаны в [правилах продукта](./docs/product/PRODUCT_RULES.md). Агенту также нужно начать с [AGENTS.md](./AGENTS.md).

## Ветки и запросы на изменение

- создавайте ветку от актуальной `develop`;
- не смешивайте исправление с несвязанным рефакторингом;
- добавляйте тест для изменённого поведения;
- объясняйте в запросе пользовательский результат, способ проверки и известные ограничения;
- используйте Conventional Commits, например `fix: исправить сохранение обзора`.

Размер файла сам по себе не является нарушением. Выделяйте модуль, когда у него появилась отдельная ответственность, независимая проверка или второй реальный потребитель.

Не добавляйте секреты, реальные пользовательские данные, локальные пути и внутренние рабочие заметки. Граница публичных материалов описана в [правилах публичного репозитория](./docs/operations/PUBLIC_REPOSITORY.md). Об уязвимостях сообщайте по [инструкции безопасности](./SECURITY.md), а не в публичной задаче.
