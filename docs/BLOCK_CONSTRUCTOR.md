# Ограниченный конструктор блоков

Статус: продуктовое решение принято, реализация отложена до завершения остальных задач текущего бэклога.

## Решение

Не создавать свободный конструктор произвольных форм. Нужен ограниченный редактор блоков на основе шаблонов, где тип каждого поля заранее определяет хранение, допустимую агрегацию, график и ограничения интерпретации.

Первый критерий блока — не возможность собрать форму, а полезный цикл:

1. понятный вопрос или решение пользователя;
2. низкозатратный ежедневный ввод;
3. однозначно типизированные значения;
4. подходящая сводка или график;
5. осторожный вывод и возможное действие.

Сбор данных без последующего решения считается пустым трекингом и не должен поддерживаться шаблоном по умолчанию.

## Ограничения первой версии

- не более шести активных пользовательских блоков;
- не более шести аналитических полей в одном блоке;
- дополнительно допускаются одно поле факторов и одно текстовое пояснение;
- не более двенадцати активных вариантов в одном поле выбора или факторов;
- один основной показатель блока и не более двух дополнительных;
- создание блока только из шаблона, без пустого холста;
- произвольные формулы, вложенные формы и пользовательский код запрещены;
- изменение типа, единицы или смысла поля создаёт новую версию, а не переписывает историю;
- использованный блок или вариант архивируется, но не удаляется из старых записей;
- пропуск отличается от явного ответа «нет» или «ничего из списка»;
- медицинские шаблоны, диагнозы и интерпретации не входят в первую версию.

«Необычный день», «Факт дня», события, итоги и временный эксперимент остаются системными сущностями и не входят в лимит пользовательских блоков.

## Начальная библиотека

Текущая конфигурация приложения становится первой проверенной библиотекой, а не заменяется абстрактной схемой:

1. сон и восстановление;
2. работа и карьера;
3. текущая цель или проект;
4. активность и тренировки;
5. питание и показатели тела;
6. области жизни или личные практики.

Пользователь сможет скрывать, переименовывать и переставлять эти блоки. Позже библиотека может получить пресеты внутри шаблона, например «Бег» для активности.

## Типы полей и визуализация

| Тип | Пример | Допустимое отображение |
| --- | --- | --- |
| Продолжительность | время бега, практики или сна | линия; сумма или среднее периода согласно определению |
| Число с единицей | километры, вес | линия; сумма, среднее или последнее значение согласно определению |
| Шкала | энергия или субъективная нагрузка | линия, распределение, среднее с числом наблюдений |
| Да / нет / пропуск | состоялась ли тренировка | частота и доля только от отмеченных дней |
| Один вариант | тип действия | распределение и частота вариантов |
| Несколько вариантов | условия или мешающие факторы | частота; сравнение с заранее связанным показателем при достаточной выборке |
| Время суток | начало активности | хронология; без автоматического среднего в первой версии |
| Текст | пояснение | журнал и экспорт без числового графика |

Для числового поля обязательны единица, допустимый диапазон и смысл агрегации. Приложение не угадывает их по названию.

## Пример «Бег»

- была ли пробежка: да / нет / не отмечено;
- продолжительность в минутах;
- дистанция в километрах;
- субъективная нагрузка с подписанными границами шкалы;
- пользовательские факторы;
- необязательное пояснение;
- темп как шаблонное вычисление только при наличии положительных дистанции и времени.

Автоматические представления: количество пробежек, недельная дистанция, продолжительность, темп по фактическим тренировкам, нагрузка и частота факторов. Фактор может сравниваться с основным показателем только как связь, а не доказанная причина.

## Доказательность

Нужно различать:

- наблюдаемый факт: дистанция, длительность, наличие действия;
- субъективную оценку: энергия или нагрузка по явно подписанной шкале;
- личную гипотезу: возможная связь фактора с показателем.

Конструктор не делает пользовательское поле научно валидированным. Для встроенного шаблона фиксируются источник и свойства измерения, решение пользователя, основной показатель, агрегация, минимальная выборка и ограничения вывода. Пользовательские поля явно остаются личными измерениями.

Основания решения:

- модель personal informatics требует рассматривать подготовку, сбор, интеграцию, рефлексию и действие как одну цепочку: https://doi.org/10.1145/1753326.1753409;
- длинные повторяющиеся анкеты повышают нагрузку и могут ухудшать качество ответов: https://doi.org/10.1177/1073191120957102;
- цели трекинга меняются, а паузы и возобновление являются нормальной частью использования: https://doi.org/10.1145/2750858.2804250;
- для N-of-1 наблюдений важны заранее выбранный результат, стабильный способ измерения и определённые периоды: https://doi.org/10.1136/bmj.h1793.

## Версионирование данных

Определения блоков не должны храниться только внутри общих настроек. Целевая модель разделяет:

- определение блока и его статус;
- неизменяемую версию блока с датой начала действия;
- определения полей со стабильными идентификаторами;
- порядок активных блоков в пользовательском профиле;
- ежедневную запись значений, связанную с конкретной версией;
- явный список отмеченных полей для различения пропуска и пустого ответа.

Изменение подписи без изменения смысла может сохранять идентификатор. Изменение единицы, типа, диапазона шкалы или интерпретации создаёт новый ряд данных.

## Порядок реализации

1. Описать существующие блоки новой схемой без видимого изменения интерфейса.
2. Добавить адаптер чтения старого `DailyEntry`, не переписывая историю сразу.
3. Создать универсальный renderer поддерживаемых типов полей.
4. Создать реестр «тип поля — сводка — график — ограничения».
5. Перевести существующие обзоры и графики на этот реестр.
6. Добавить переименование, порядок, факторы и архивирование.
7. Разрешить создание блока только из шаблона.
8. Проверить модель на текущей конфигурации и пресете «Бег».

Каждый этап выполняется отдельным вертикальным срезом с миграционными и сценарными тестами. До начала реализации нужно утвердить схему сущностей и матрицу допустимой аналитики.
