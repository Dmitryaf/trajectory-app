# Аудит системы — 22 июля 2026

## Итог

Текущая версия пригодна для дальнейшей разработки: проверенные пользовательские сценарии работают, production-сборка воспроизводится, известных уязвимостей в production-зависимостях не найдено, а текущая схема Supabase ограничивает снимок владельцем записи через RLS.

Архитектура не является законченной слоистой системой. Это управляемый переходный монолит, в котором экспорт, журнал, синхронизация, аналитика и жизненный цикл ежедневной записи уже получили отдельные функциональные границы. Общие `types.ts`, `SettingsView.vue` и `style.css` всё ещё крупные, но массовая перекладка файлов принесёт больше риска, чем пользы; разделение продолжается только вместе с реальным сценарием и тестами.

В ходе аудита исправлены два риска облачной синхронизации:

- одновременные реакции на восстановление сессии больше не запускают параллельную загрузку приложения;
- локальное изменение помечается ожидающим синхронизации до начала сетевого запроса, поэтому закрытие приложения или обрыв сети не создают ложный статус «синхронизировано».

## Что проверено

- модель и миграции ежедневных записей, итогов, событий, обзоров и настроек;
- IndexedDB, импорт/экспорт и стартовое согласование с облачной копией;
- авторизация Supabase и политики `trajectory_snapshots`;
- вычисления недели, месяца и трендов, особые дни и достаточность данных;
- прежние продуктовые исправления из заметок владельца;
- маршрутизация SPA, PWA-кэш, Vercel rewrites и восстановление после устаревшего чанка;
- автоматические тесты, Husky, commitlint и CI;
- границы слоёв, размеры исходных файлов и production-чанков;
- текущее дерево на отслеживаемые env-файлы и очевидные секреты;
- production-зависимости через `npm audit --omit=dev`.

## Найденные риски и приоритет

### P0 — локальные блокирующие риски закрыты

1. **Граница снимка усилена.** Файл и облачная копия проходят общую проверку и нормализацию до транзакции; повреждённые данные не очищают IndexedDB. Совместимость версий 1–3 и ошибочные записи покрыты тестами.
2. **Staging подтверждён.** `develop` разворачивается отдельно от production, использует собственный Supabase и тестового пользователя; вход, запись и изоляция вручную проверены. GitHub rulesets остаются недоступны на текущем тарифе и заменены процессным правилом.
3. **Ежедневная запись защищена.** Dirty-state блокирует случайную смену даты, маршрута и закрытие вкладки; локальная ошибка сохранения не очищает draft.

Внешний запуск пользователей по-прежнему заблокирован политикой данных и полным удалением аккаунта, но это отдельная продуктовая граница, а не дефект текущего личного режима.

### P1 — ближайшие архитектурные срезы

1. Стартовая синхронизация вынесена в `features/sync`, журнал — в `features/journal`, аналитика разделена на чистые модули, а draft ежедневной записи — на `model.ts` и `useDailyEntryForm.ts`.
2. `SettingsView.vue` разделять только вместе со следующим изменением конкретного сценария: ежедневные блоки, пользовательские варианты, эксперимент, облако или резервные копии.
3. Браузерный раннер проверяет Clipboard/Download API недельного обзора и мобильное сохранение dirty-state ежедневной записи. Следующие сценарии — вход, восстановление из облака и конфликт версий — добавлять после определения безопасной тестовой границы Supabase.
4. Не начинать ограниченный конструктор, пока граница настраиваемых блоков и постоянного ядра ежедневной записи не закреплена в модели.

### P2 — производительность и сопровождение

1. ECharts подключён модульно через `echarts/core` и находится в ленивом чанке страниц обзора. `check:dist` теперь ограничивает gzip-размер начального JS, CSS и любого JS-чанка; предупреждение Vite не скрывается повышением лимита.
2. `style.css` остаётся монолитом примерно на 65 КБ исходного CSS. Его стоит делить вслед за функциональными срезами, а не по произвольным категориям.
3. Storybook полезен для уже стабильных компонентов, но не заменяет сценарные и E2E-тесты. Начать с существующих полей, кнопок, карточек и граничных состояний.
4. В корне остаётся внутренняя инструкция `BACKEND_AUTH_CI.md`; перед публикацией она и ссылки на внутреннюю документацию должны исчезнуть из публичной истории.
5. В достижимой истории есть старый commit message с упоминанием Codex. Очистка истории остаётся отдельной разрушительной операцией только по явному разрешению.

## Состояние слоёв

```text
views  -> features + stores + shared UI
features/daily-entry -> чистая модель + жизненный цикл draft
features/analytics   -> сводки + наблюдения + сравнения + подсказки
features/export      -> чистый report + browser adapter
features/journal     -> фильтры + диапазон + пагинация
features/sync        -> стартовая облачная сверка
stores -> IndexedDB + состояние + очередь облачного снимка
components -> переиспользуемый UI
```

Положительная часть: чистая подготовка AI-отчёта отделена от Clipboard/Blob API, браузерные маршруты ленивые, база инкапсулирована store, а компоненты графиков не содержат продуктовых расчётов.

Оставшаяся переходная граница: `SettingsView.vue` знает несколько независимых сценариев, страницы пока собирают готовые аналитические модули, а store одновременно отвечает за состояние, IndexedDB и очередь облачного снимка. Это не блокирует приложение сегодня. Конструктор остаётся последним крупным изменением после стабилизации границ данных и функций.

## Очерёдность после аудита

1. Расширить браузерные проверки на вход и критичные сценарии облака через отдельную безопасную тестовую границу Supabase.
2. Разделять настройки только вместе с конкретным продуктовым изменением, не ради структуры папок.
3. Продолжить остаточную визуальную полировку по одному экрану и с реальными данными.
4. Landing оставить ниже текущих продуктовых задач.
5. Подготовку публичной истории проводить отдельной разрешённой операцией.
6. Ограниченный конструктор блоков — только после остальных актуальных пунктов.
