# Самопроверка

## Для каждого блока

1. Повторно прочитать изменённый код и проверить пустые, старые и граничные данные.
2. Убедиться, что пользователь видит успех или понятную ошибку.
3. Если затронут интерфейс, выбрать по риску представительные состояния: пустые и заполненные данные, новая и существующая запись, чистая и изменённая форма, включённые и выключенные условные блоки. Не перебирать механически все сочетания, но обязательно проверять сочетание, в котором ошибка наиболее вероятна или дорога.
4. Проверить мобильную, промежуточную планшетную и настольную ширину, клавиатурный ввод, длинные списки и длинный пользовательский текст, если они относятся к изменённому сценарию. Для блока, который выводит ограниченное текстовое поле, стандартный граничный сценарий — непрерывная строка без пробелов близко к максимальной длине: она не создаёт горизонтальную прокрутку, не выходит за контейнер и не вытесняет соседние действия.
5. Для модального окна проверить явное закрытие, `Escape`, клик по фону и последовательность «нажать внутри окна — отпустить за его пределами». Последняя не должна закрывать окно; кнопка закрытия сохраняет доступное имя, достаточную область нажатия и визуальное центрирование при поддерживаемых ширинах и масштабе.
6. Если значим визуальный результат, проверять не только видимость элементов, но и нужное отношение между ними: порядок, расстояние, отсутствие перекрытия, принадлежность содержимого заголовку и положение закреплённого элемента относительно навигации. Использовать устойчивую геометрическую проверку либо визуальный снимок в стабильном окружении.
7. Для условно отображаемых фильтров, подписей и команд проверить стабильность высоты блока до и после действия. Часто используемый сброс не должен появляться только после активации фильтра и сдвигать соседний интерфейс.
8. Для перенесённой, заменённой или удалённой функции проверить оба результата: новый путь доступен, незапланированный старый путь отсутствует. Зелёный тест нового компонента не доказывает отсутствие дублирующего интерфейса.
9. Добавить или обновить тест для расчёта, преобразования или миграции, где это возможно.
10. Сверить терминологию во всех затронутых экранах, экспорте и документации.

## Перед передачей результата

Во время работы сначала выполнить релевантный точечный тест. После последнего изменения кода или конфигурации один раз выполнить полный gate:

```text
npm run check
git diff --check
git status --short
```

Если следующий pre-commit запускает тот же `npm run check` и после него код не менялся, отдельный ручной полный запуск не нужен. Для изменений только Markdown достаточно `git diff --cached --check` и проверки изменённых ссылок; CI всё равно выполняет полный gate после push.

Если менялись Clipboard/Download API, маршруты, вход или облачная сверка, дополнительно выполнить `npm run test:e2e`. Первый локальный запуск требует `npx playwright install chromium webkit`; CI устанавливает оба браузерных движка отдельно. Пиксельные эталоны проверяются только в Chromium, а поведенческие сценарии — также в desktop WebKit; критические мобильные сценарии дополнительно запускаются с профилем Mobile Safari. Эта эмуляция не заменяет ручную проверку на реальном устройстве перед публичным выпуском.

Затем проверить diff на:

- случайные файлы сборки и секреты;
- отладочный вывод и временный код;
- необработанные ошибки асинхронных действий;
- потерю старых данных при нормализации;
- вывод будущих или вымышленных значений;
- лишние изменения вне текущего блока.

Перед созданием каждого коммита дополнительно проверить staged-набор:

```text
git diff --cached --stat
git diff --cached --check
```

Если staged-набор содержит несколько независимых результатов или приближается к тысяче изменённых строк, вернуться к разбиению коммитов.

Готовность означает не только успешную сборку, но и завершённый пользовательский сценарий.

## Проверка SPA/PWA перед продом

Если изменены маршруты, Vite/PWA, service worker, настройки Vercel или стратегия сборки:

1. Проверить прямое открытие всех клиентских маршрутов.
2. Убедиться, что JavaScript и CSS из production HTML отвечают кодом `200` и корректным `Content-Type`.
3. Проверить, что отсутствующий `/assets/*.js` отвечает кодом `404`, а не содержимым `index.html`.
4. Убедиться, что SPA- и navigation fallback не применяются к `/assets` и `/api`.
5. Проверить стратегию кэширования: HTML и service worker должны перепроверяться, а файлы с хешем в имени могут кэшироваться как immutable.
6. После публикации проверить свежую сессию и уже открытую вкладку при обновлении service worker. Ошибка загрузки старого dynamic import должна приводить к контролируемому обновлению, а не к падению страницы.

## Git hooks

- `pre-commit` запускает `npm run check` для кода, конфигурации и зависимостей; для чисто документационного staged-набора выполняет только `git diff --cached --check`;
- `commit-msg` проверяет Conventional Commits через commitlint;
- допустимый формат: `type: короткое описание`, например `fix: исправить экспорт данных`;
- основные типы: `feat`, `fix`, `docs`, `test`, `refactor`, `build`, `ci`, `chore`;
- хуки устанавливаются командой `npm run prepare`, которая также выполняется после `npm install`;
- обход через `--no-verify` допустим только для осознанной диагностики, а не для принятия непрошедшего изменения.
