# Ветки и среды поставки

Этот процесс отделяет разработку и ручную проверку от production. Он не заменяет тесты: каждое изменение сначала проходит CI, затем проверяется в Preview или staging и только после этого попадает в `main`.

## Роли веток

- `main` — только проверенные production-релизы;
- `develop` — общая версия следующего релиза и постоянный staging;
- `feature/*`, `fix/*`, `docs/*`, `refactor/*`, `ci/*` — короткие ветки одной задачи.

Обычный путь изменения:

```text
короткая ветка -> pull request в develop -> Preview -> staging -> release PR в main -> production
```

Срочное исправление создаётся от `main`, отдельно проверяется и после production вливается также в `develop`.

## Что проверяет репозиторий

Workflow `.github/workflows/ci.yml` запускается:

- для pull request в `develop` и `main`;
- для push в `develop` и `main`.

CI использует версию Node.js из `.nvmrc`, устанавливает точные зависимости через `npm ci` и запускает `npm run check` — тесты, production-сборку, smoke-проверку и статическую сборку Storybook. После этого CI устанавливает Chromium Playwright и выполняет отдельные браузерные сценарии через `npm run test:e2e`.

## Первичная настройка GitHub

После публикации ветки `develop` настроить rulesets или branch protection для `develop` и `main`:

1. Запретить удаление и force-push обеих веток.
2. Требовать pull request перед изменением защищённой ветки.
3. Сделать проверку `test-and-build` обязательной и требовать актуальную ветку перед merge.
4. Запретить merge при нерешённых обсуждениях.
5. Для личного репозитория не требовать одобрение второго пользователя, пока в проекте один разработчик.
6. Разрешить обход правил только для осознанного аварийного восстановления.

Рекомендуемый default branch для повседневных pull request — `develop`; production-веткой Vercel при этом остаётся `main`.

## Настройка Vercel

1. В Production environment закрепить Branch Tracking за `main`.
2. Оставить автоматические Preview deployments для коротких веток.
3. Закрепить постоянный staging-домен за Preview-веткой `develop`.
4. Назначить для `develop` отдельные Preview environment variables.
5. Не продвигать Preview в production без успешного CI и ручной smoke-проверки.

Для staging нужны отдельные значения:

```text
VITE_SUPABASE_URL=<staging project URL>
VITE_SUPABASE_ANON_KEY=<staging publishable/anon key>
```

Production-значения не должны использоваться в Preview или staging.

## Отдельный Supabase для staging

1. Создать отдельный Supabase-проект.
2. Применить все миграции из `supabase/migrations`.
3. Создать только тестового пользователя.
4. Оставить регистрацию выключенной до настройки и проверки серверного beta invite hook.
5. Проверить Row Level Security тестовым входом.
6. Не копировать личные production-записи в staging.

## Проверка перед release PR

1. CI ветки `develop` завершился успешно.
2. Staging открывает прямые маршруты и корректно обновляет PWA.
3. Вход, сохранение, синхронизация, экспорт и восстановление проверены тестовым пользователем.
4. Отсутствующий `/assets/*.js` возвращает `404`, а не `index.html`.
5. Список изменений не содержит незавершённых миграций и известных блокирующих дефектов.
6. После merge в `main` production проверяется повторно по `docs/agent/QUALITY.md`.

## Что остаётся внешней настройкой

Файлы репозитория не могут сами включить GitHub branch protection, назначить Vercel-домен или создать Supabase-проект. Эти действия выполняются один раз в интерфейсах сервисов; документ фиксирует точные ограничения, чтобы среды не расходились незаметно.

## Текущее состояние staging

На 22 июля 2026 года:

- `develop` опубликована и выбрана default branch репозитория;
- push в `develop` успешно прошёл workflow `CI`;
- Vercel отслеживает `main` как production branch и собирает `develop` как Preview;
- постоянный адрес ветки: `https://trajectory-app-git-develop-trajectory3.vercel.app`;
- Preview защищён входом Vercel и не индексируется;
- переменные production Supabase назначены только окружению Production и не попадают в Preview;
- Vercel использует Node.js 22.x в соответствии с `.nvmrc` и `package.json`;
- прямые маршруты staging отвечают `200`, JavaScript имеет корректный MIME, отсутствующий asset возвращает `404`;
- отдельный custom environment недоступен на текущем тарифе Vercel, поэтому постоянным staging служит Preview ветки `develop`;
- GitHub rulesets для приватного репозитория недоступны на текущем тарифе. До перехода на GitHub Pro или открытия репозитория запрет прямого push остаётся процессным правилом;
- отдельный Supabase `trajectory-app-staging` создан в `eu-west-1`, схема применяется через `supabase/migrations`, а его публичные ключи назначены только Preview ветки `develop`;
- публичная регистрация и анонимный вход в staging отключены, email-вход для заранее созданного пользователя включён;
- сквозная проверка временными пользователями подтвердила вход, запись снимка и RLS: второй пользователь не видит чужую строку; временные пользователи после проверки удалены;
- постоянный подтверждённый тестовый пользователь создан владельцем вручную; его пароль не попал в терминал, репозиторий или историю переписки;
- ручной smoke под тестовым пользователем успешно пройден: вход, импорт снимка, сохранение после перезагрузки, копирование промпта и скачивание данных работают.

Перед включением самостоятельной beta-регистрации выполнить порядок из `BACKEND_AUTH_CI.md`: migration → код и лимит → Auth Hook → email/SMTP и rate limits → Supabase signup → frontend-флаг. CAPTCHA добавляется только вместе с совместимым интерфейсом и при реальном риске автоматических попыток. Production не включается одновременно со staging и получает другой код приглашения.
