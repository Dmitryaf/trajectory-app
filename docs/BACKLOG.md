# Бэклог после заметок 21 июля 2026

## Следующий этап: визуальный дизайн

Начать с поверхностей «Сегодня», обзоров периода и «Журнала» по плану из `DESIGN_AUDIT.md`. Сначала подготовить визуальное направление и токены, затем обновлять экраны по одному с проверкой мобильной ширины и реальных длинных данных.

## Следующий продуктовый блок: сменяемые фокусы

Не делать произвольный конструктор полей поверх текущей модели. Сначала спроектировать профиль фокуса:

- включаемые блоки ежедневной записи;
- пользовательские факторы и варианты ответа;
- дата действия профиля, чтобы смена приоритета не переписывала историю;
- явные типы показателей для графиков: число, шкала, один выбор, несколько вариантов, факт;
- правила достаточности данных и допустимые сравнения для каждого типа.

Первый безопасный этап — разрешить скрывать сон, карьеру, питание и движение из ежедневной формы, сохраняя старые данные и аналитику. Универсальные графики и таблицы требуют отдельной версии схемы и миграции.

## Архитектура

Перед конструктором разделить приложение по функциям: daily-entry, journal, reviews, analytics, settings, sync и export. Внутри каждой функции отделить модель, вычисления, хранение и UI. Делать это по одному вертикальному сценарию с тестами, а не переносить все файлы одновременно.

## Дальнейшее тестирование

- добавить компонентные тесты основных форм и навигации;
- добавить интеграционный тест импорта и восстановления старого снимка;
- при появлении форматтера добавить staged-проверки без автоматического изменения пользовательских файлов.

## Подготовка к публичному репозиторию

Проводить отдельной задачей с явным разрешением на переписывание истории:

- инвентаризация секретов, личных данных, тестовых снимков и служебных документов во всех достижимых коммитах;
- проверка упоминаний инструментов разработки и неуместных сообщений коммитов;
- решение, какие демонстрационные данные допустимы публично;
- очистка истории, повторная проверка объектов Git, ротация найденных ключей и только затем force-push;
- публичный README, лицензия, security policy и шаблон конфигурации без секретов.

## Ветки и среды поставки

Не отправлять каждую завершённую доработку сразу в production.

- `main` содержит только проверенные релизы и остаётся production-веткой;
- `develop` служит интеграционной веткой для общей проверки нескольких изменений;
- каждая задача выполняется в короткой ветке `feature/*`, `fix/*`, `docs/*` или `refactor/*`;
- pull request задачи направляется в `develop` и получает отдельный Vercel Preview;
- обновление `develop` разворачивается в постоянную staging-среду для ручной проверки связанных сценариев;
- релизный pull request из `develop` в `main` создаётся только после CI, smoke-проверки и просмотра накопленного списка изменений;
- staging использует отдельный проект Supabase, отдельные переменные окружения и тестового пользователя — production-данные и ключи не переиспользуются;
- срочное исправление идёт через `fix/*`, проверяется отдельно и после production возвращается в `develop`, чтобы ветки не расходились.

При внедрении обновить GitHub branch protection, Vercel environments, CI workflow и документацию выпуска.

## Визуальный дизайн

Сначала провести аудит и выбрать 2–3 ключевые поверхности: ежедневная запись, обзор периода и журнал. Усилить иерархию, акцентные состояния и различимость графиков, не добавляя декоративный шум и новые цвета без семантики.
