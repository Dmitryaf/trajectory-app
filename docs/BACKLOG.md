# Приоритетный бэклог на 22 июля 2026

Приоритеты пересматриваются после каждого нового пула заметок. Внутри каждого уровня задачи расположены от более важной к менее важной.

- `P0` — защита данных и production, блокирующие дефекты;
- `P1` — заметное влияние на основной пользовательский сценарий;
- `P2` — развитие продукта и удобства без срочного риска;
- `P3` — подготовительные и второстепенные улучшения.

## P0 — надёжность разработки и поставки

Полный снимок состояния и основания приоритетов зафиксированы в `docs/SYSTEM_AUDIT_2026-07-22.md`.

### 1. Ветки, preview и staging

Не отправлять каждую завершённую доработку сразу в production.

Репозиторная часть начата: CI, шаблон pull request и процедура поставки описаны в `docs/DELIVERY.md`. До завершения остаются публикация `develop` и внешняя настройка GitHub, Vercel и отдельного Supabase.

- `main` содержит только проверенные релизы и остаётся production-веткой;
- `develop` служит интеграционной веткой для общей проверки нескольких изменений;
- каждая задача выполняется в короткой ветке `feature/*`, `fix/*`, `docs/*` или `refactor/*`;
- pull request задачи направляется в `develop` и получает отдельный Vercel Preview;
- обновление `develop` разворачивается в постоянную staging-среду;
- релизный pull request из `develop` в `main` создаётся только после CI, smoke-проверки и просмотра списка изменений;
- staging использует отдельный проект Supabase, переменные окружения и тестового пользователя;
- срочное исправление после production возвращается в `develop`, чтобы ветки не расходились.

При внедрении обновить GitHub branch protection, Vercel environments, CI и документацию выпуска.

### 2. Строгая граница резервных и облачных копий

До следующего production-релиза валидировать и нормализовать весь снимок до очистки IndexedDB:

- проверять каждый тип записи, обязательные ключи, даты и допустимые числовые диапазоны;
- удалять неизвестные значения перечислений без подмены их нулями;
- сохранять совместимость с версиями резервных копий 1–3;
- применять снимок атомарно только после успешной подготовки;
- одинаково использовать границу для загрузки файла и облачной копии;
- покрыть повреждённые и частично устаревшие копии тестами.

Выполнено: `features/backup` проверяет структуру и даты всего снимка до транзакции, нормализует числовые и перечислимые значения без подмены нулями и одинаково используется файлом и облаком. Ошибочный снимок не очищает текущую базу; совместимость версий 1–3 и повреждённые записи покрыты тестами.

### 3. Регрессионные тесты ключевых сценариев

- добавлена smoke-проверка production-сборки и конфигурации SPA/PWA;
- добавлен интеграционный тест импорта старой резервной копии и сохранности данных при ошибке формата;
- добавлены компонентные тесты длительности, множественного выбора и навигации по периодам;
- добавлены сценарные тесты сохранения ежедневной записи и работы журнала;
- при появлении форматтера добавить staged-проверки без автоматического изменения пользовательских файлов.

## P1 — основной пользовательский опыт

### 4. Аудит и упрощение текстов

Проверить заголовки, пояснения, placeholders, пустые состояния и экспорт. Убрать формулировки, которые предполагают конкретную карьерную цель, личный словарь владельца или понимание абстракций вроде «движения» и «траектории» без пояснения.

Текст должен прямо отвечать на вопросы: что сюда записать, зачем это нужно и где запись появится. Примеры должны подходить людям с разными целями и образом жизни.

Выполнен первый сквозной проход по ежедневной записи, журналу, обзорам, трендам, настройкам и автоматическим наблюдениям. Следующий повторный проход нужен после внедрения сменяемых целей и блоков записи.

### 5. Читаемый пакет для ручного AI-анализа

Скопированный промпт не должен содержать большой технический JSON без необходимости.

- подготовить компактное человекочитаемое описание периода и данных;
- передавать только поля, которые нужны для выбранного анализа;
- заменить внутренние идентификаторы понятными подписями;
- отделить промпт для копирования от полного lossless JSON для скачивания;
- сохранить предупреждение о личных данных и ограничения выводов;
- добавить тесты состава и размера пакета.

Выполнено: копируемый промпт использует компактную человекочитаемую сводку без технических идентификаторов, временных полей и JSON-разметки. Полный JSON остаётся отдельной lossless-выгрузкой; состав и относительный размер промпта защищены тестом.

### 6. Поэтапное разделение архитектуры

Перед расширением модели разделить приложение по функциям: daily-entry, journal, reviews, analytics, settings, sync и export. Внутри каждой функции отделить модель, вычисления, хранение и UI.

Проводить рефакторинг по одному вертикальному сценарию с тестами, не переносить все файлы одновременно и не останавливать продуктовую разработку ради идеальной структуры.

Начат первый вертикальный срез: экспорт и ручной анализ вынесены в `src/features/export`, чистая подготовка отчёта отделена от браузерных операций. Целевые границы и правила следующих переносов зафиксированы в `docs/ARCHITECTURE.md`.

## P2 — развитие удобства и продукта

### 7. Длинные инсайты без требования заранее их структурировать

Не заставлять пользователя разбивать живую мысль на несколько записей. Перед изменением проверить реальные длины и сценарии редактирования.

Предпочтительное направление: автоматически растущее поле, более высокий безопасный лимит и сохранение одной цельной записи. Темы или метки можно предложить позже как необязательную организацию, а не как условие сохранения.

Выполнено: заметка события или инсайта принимает до 2000 символов и растёт по мере ввода до ограниченной высоты. Длинная мысль сохраняется одной записью; в архиве она сворачивается до четырёх строк и раскрывается по запросу, поэтому список не растягивается без необходимости.

### 8. Начальный диапазон фильтров по датам

При открытии архива устанавливать `С = сегодня`, а поле `По` оставлять пустым. Так длинная история не разворачивается сразу, но пользователь может выбрать любой последующий диапазон.

Активный фильтр должен быть заметен. Рядом нужна быстрая команда «За всё время», которая очищает обе границы. Выбранный диапазон сохраняется до ухода со страницы и одинаково работает в «Итогах» и «Событиях».

Выполнено: обе страницы открываются с начальной датой, равной сегодняшней, и пустой конечной датой. Активный диапазон выделен и подписан, а команда «За всё время» очищает обе границы. Пагинация по восемь записей продолжает ограничивать длину страницы.

### 9. Storybook для переиспользуемых компонентов

Подключить после определения стабильных UI-компонентов и сценариев. Начать с кнопок, полей, групп выбора, карточек метрик, пустых состояний и длинных текстовых данных. Добавить светлые, мобильные, loading/error/empty и граничные состояния; запускать проверку Storybook в CI.

### 10. Отдельная аннотация или landing приложения

Объяснить простым языком:

- какую проблему решает приложение;
- как выглядит ежедневный, недельный и месячный сценарий;
- какие данные сохраняются и как используются;
- чего приложение не обещает и почему не оценивает человека;
- чем оно отличается от списка задач и обычного дневника.

До реализации решить, должен ли это быть публичный landing, экран до входа или раздел справки внутри приложения.

### 11. Подготовка к публичному репозиторию

Проводить отдельной задачей с явным разрешением на переписывание истории:

- инвентаризация секретов, личных данных и тестовых снимков во всех достижимых коммитах;
- проверка служебных документов и неуместных сообщений коммитов;
- решение о допустимых демонстрационных данных;
- очистка истории, повторная проверка объектов Git и ротация найденных ключей;
- публичный README, лицензия, security policy и шаблон конфигурации без секретов.

Публичная граница определена в `docs/PUBLIC_REPOSITORY.md`. Внешнему пользователю остаются продуктовый README, код, тесты и необходимые публичные инструкции. Правила агента, бэклог, аудиты, продуктовые гипотезы, внутренняя архитектура и инструкции окружения считаются локальной «кухней» и должны быть удалены из всей достижимой истории перед публикацией. Простого добавления этих путей в `.gitignore` недостаточно.

## P3 — визуальная полировка

### 12. Остаточная доработка визуального дизайна

Продолжать по одному экрану и только там, где изменение улучшает иерархию, чтение длинных данных или различимость состояния. Сверяться с `DESIGN_AUDIT.md`, мобильной шириной и реальными записями; не добавлять декоративный шум и цвета без семантики.

### 13. Система анимаций

Сначала определить ограниченный набор переходов: появление обратной связи, раскрытие секций, смена периода и добавление записи. Анимации должны объяснять изменение состояния, учитывать `prefers-reduced-motion`, не задерживать ввод и не маскировать загрузку.

## Отложено до завершения остального бэклога

### 14. Сменяемые фокусы и ограниченный конструктор блоков

Не делать произвольный конструктор полей поверх текущей модели. Первый безопасный этап уже выполнен: сон, карьеру, питание и движение можно скрывать без удаления исторических данных.

Решение следующего этапа зафиксировано в `docs/BLOCK_CONSTRUCTOR.md`: максимум шесть активных блоков, создание только из шаблонов, типизированные поля, версии конфигурации и реестр допустимой аналитики. Реализация начинается только после выполнения всех остальных актуальных пунктов этого бэклога и повторной проверки границ данных.
