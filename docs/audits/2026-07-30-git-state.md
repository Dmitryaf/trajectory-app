# Состояние Git на 30 июля 2026 года

Это датированный аудит состояния репозитория на 30 июля 2026 года.
Он не является текущей инструкцией по Git и после изменения веток может устареть.
Актуальный рабочий процесс находится в [DELIVERY.md](../operations/DELIVERY.md).

## Область и ограничения проверки

Аудит основан на локальных refs, `git status`, графе достижимых commit и конфигурации репозитория. Во время проверки не выполнялись `fetch`, `pull`, переключение веток и любые изменяющие историю операции.

GitHub CLI в среде отсутствует, а приватное состояние GitHub не удалось открыть без авторизации. Поэтому branch protection и список GitHub Releases не проверены напрямую. Документ доставки фиксирует, что rulesets приватного репозитория были недоступны на используемом тарифе; это внешнее состояние может измениться.

## Merge-коммиты и форма истории

Во всей достижимой локальной истории найдено два commit с двумя родителями:

- `aa71af9` от 22 июля — ручное объединение release-ветки с `develop`; родители `36ee652` и `404b8fb`;
- `a704976` от 22 июля — объединение получившегося `develop` с `main`; родители `876bdf3` и `aa71af9`.

Остальные прошлые объединения могли быть fast-forward, squash или прямым обновлением удалённой ветки. PR является объектом GitHub и не обязан оставлять merge-коммит, поэтому количество PR нельзя восстановить только по `git log`.

Сами два merge-коммита не означают повреждение истории. Основная проблема — отсутствие понятного повторяемого процесса и разное состояние одноимённых локальных и удалённых веток.

## Почему появлялась команда Publish Branch

В редакторе Publish Branch означает первый push локальной ветки с настройкой upstream, а не выпуск релиза. Кнопка могла появиться при уже существующей одноимённой ветке GitHub, если локальная ветка не была связана с ней, remote-tracking refs были устаревшими или истории разошлись.

Проверять связь нужно через `git branch -vv` и `git status -sb`. Наличие одинакового имени локально и на GitHub само по себе не доказывает настроенный upstream.

## Почему локальные `main` и `develop` отстали

Прошлые поставки напрямую двигали удалённые `main` и `develop` из другой рабочей ветки. GitHub получил commits, но одноимённые локальные ветки автоматически не переместились. Это объясняет одновременно линейную часть истории и большое отставание локальных refs.

Такое состояние не требует force-push или переписывания опубликованной истории. Долгоживущие локальные ветки позже можно обновить fast-forward, но только после завершения и фиксации текущего документального блока.

## Шумный CSS-diff

Commit `0f04350` называется `fix: fixed feedback button display` и изменяет только `src/style.css`, но его статистика — 4203 добавления и 780 удалений. Функциональное исправление смешано с массовым форматированием почти всего файла.

Commit находится в `fix/beta-readiness` поверх известного `origin/develop` и ещё не входит в известные `origin/develop` или `origin/main`. Переписывать опубликованный commit не требуется. Безопаснее отдельным проверяемым commit вернуть нерелевантное форматирование и оставить только минимальный CSS-diff исправления.

## Незакоммиченные документы

На момент аудита working tree содержит единый незавершённый документальный блок:

- перенос существующих материалов из корня и `docs/` в тематические каталоги;
- обновление `README.md`, `docs/AGENTS.md` и инструкций агента;
- новый разбор заметок беты;
- создание руководства владельца и этого аудита.

До разделения или фиксации этого блока переключение веток, pull, merge и rebase создают лишний риск смешать документацию с другим изменением. Git показывает старые пути удалёнными, а новые каталоги неотслеживаемыми, пока перемещения не подготовлены в index; это ожидаемо для текущего unstaged-состояния.

## Безопасная последовательность именно для этого состояния

Эти действия выполнять позже, отдельным осознанным этапом, а не в рамках аудита:

1. Завершить документацию и проверить все новые и удалённые пути.
2. Просмотреть полный diff, убедиться, что в нём нет production-кода, секретов и случайных файлов.
3. Подготовить только документальный набор и проверить, какие удаления Git распознал как перемещения.
4. Зафиксировать документацию отдельным commit после явного разрешения владельца.
5. Отдельно очистить форматирующий шум `0f04350`, сохранив функциональное исправление feedback.
6. Проверить итог ветки относительно `origin/develop` и пройти профильные проверки.
7. Создать task PR в `develop`, потому что действующий staging привязан к этой ветке.
8. Только после merge и чистого working tree обновить локальные `develop` и `main` fast-forward-командами из `DELIVERY.md`.

Перед любым удалением старой локальной ветки нужно подтвердить судьбу её изменений. После squash merge исходный commit короткой ветки не становится предком целевой ветки, поэтому отказ `git branch -d` сам по себе не означает, что PR не был объединён.

## Опасные команды, которые сейчас запрещены

Пока документальный блок не завершён и не проверен, не выполнять:

- `git switch` или `git checkout` на другую ветку;
- `git pull`, `git merge` или `git rebase`;
- `git reset --hard`;
- `git push --force` и `git push --force-with-lease`;
- интерактивный rebase опубликованной истории;
- массовое удаление веток;
- `git add .` без предварительного просмотра точного состава изменений.

Особенно нельзя выравнивать локальные ветки через hard reset: текущее расхождение объяснимо и исправляется без потери истории после завершения working tree.
