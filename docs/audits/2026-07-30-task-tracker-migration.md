Стратегические направления, ещё не подтверждённые идеи и постоянные ограничения должны остаться вне доски до появления конкретной работы.

## 4. Рекомендуемая структура GitHub Project

Название: **Траектория — работа**.

Репозиторий использует один Project. Основное представление — board, сгруппированный по `Status`. Отдельные Projects для беты, разработки и документации не нужны: области различаются полем `Area`.

### Status

| Значение | Когда использовать |
|---|---|
| `Inbox` | Новая карточка ещё не проверена на дубль, конкретность и приоритет. |
| `Ready` | Понятны проблема, результат, критерии готовности и ограничения; задачу можно брать в работу. |
| `In progress` | Работа фактически начата. Для одного исполнителя рекомендуется не держать более одной основной карточки одновременно. |
| `Review` | Есть результат, который ждёт code review, Preview/staging или другой оговорённой проверки. |
| `Done` | Критерии готовности выполнены, Issue закрыта. |

### Поля

Дополнительные поля не нужны.

| Поле | Значения | Правило |
|---|---|---|
| `Priority` | `P0`, `P1`, `P2`, `P3` | Сохраняет уже принятую продуктовую шкалу. `P0` — данные и безопасная эксплуатация; `P1` — основной сценарий и сигнал беты; `P2` — удобство и поставка; `P3` — работа после подтверждения сценария. |
| `Area` | `Today`, `Week`, `Month`, `Trends`, `Analytics`, `Sync`, `Auth`, `Settings`, `Data`, `Infrastructure`, `Documentation` | Выбирается по главной затронутой области. Для сквозной задачи используется наиболее ответственный контур, а не список меток. |
| `Size` | `S`, `M`, `L` | `S` — локальная понятная работа; `M` — несколько связанных частей и проверок; `L` — большой срез, который перед началом следует проверить на возможность декомпозиции. Это относительный размер, не обещание часов. |

### Начальная автоматизация

На старте достаточно встроенных правил:

1. новая добавленная в Project Issue получает `Inbox`;
2. закрытая Issue получает `Done`;
3. перемещение в `Ready`, `In progress` и `Review` выполняется вручную, пока процесс не устоится;
4. PR связывается с Issue штатной ссылкой закрытия, но сам PR не становится отдельной задачей на доске.

Не следует сразу добавлять GitHub Actions, отдельное поле типа работы, сроки, спринты или оценку в часах. Для текущего размера проекта это увеличит обслуживание доски без доказанной пользы.

Справочные основания: [поля GitHub Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/understanding-fields), [встроенные automation](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations) и [рекомендации по ведению Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/best-practices-for-projects).

## 6. Предлагаемый шаблон Issue

После подтверждения миграции шаблон можно добавить в `.github/ISSUE_TEMPLATE/`. Для маленькой задачи достаточно заполнить проблему, ожидаемый результат и критерии готовности; пустые необязательные разделы не должны превращаться в формальность.

```md
## Проблема

## Ожидаемый результат

## Контекст и затронутая область

## Критерии готовности

## Ограничения

## Проверки
```

Правило формулировки: Issue описывает одну проверяемую проблему и законченный результат. Стратегическое направление, общее пожелание «улучшить» или неизвестное решение остаётся в Inbox только на время уточнения либо вообще не создаётся.

## 7. Новая роль `BACKLOG.md`

После отдельного подтверждения `BACKLOG.md` следует переименовать по смыслу внутри документа в стратегический backlog и оставить в нём только следующую структуру:

```md
# Стратегический backlog

## Текущий этап

Краткая цель закрытой беты и главный проверяемый результат этапа.

## Крупные продуктовые направления

Направления без детального task-list.

## Порядок приоритетов

Принципы P0 → P3 и правило выбора следующей работы.

## Идеи, не готовые стать Issues

Идеи без checkbox: наблюдение, неизвестность и условие возврата к идее.

## Критерии перехода к следующему этапу

Проверяемые продуктовые и эксплуатационные gates.

## Текущие задачи

Текущая работа ведётся только в [GitHub Project](<ссылка после создания Project>).

## Когда идея становится Issue

- есть конкретная проблема или проверяемый вопрос;
- понятен ожидаемый результат;
- обозначены минимальные критерии готовности;
- работа достаточно ограничена для одной карточки;
- выполнен поиск дублей;
- определены Priority, Area и Size.
```

В `BACKLOG.md` не должно остаться параллельного списка текущих Issues, их статусов или checkbox. Для стратегического направления допустима ссылка на сохранённый GitHub query или Project view, но не ручное копирование карточек.

После миграции `BETA_NOTES_2026-07-30.md` остаётся датированным архивом решения. `BETA_RELEASE.md` остаётся runbook: активность запускается и отслеживается Issue, а документ объясняет последовательность и границы проверки.
