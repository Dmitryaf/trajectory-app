# Независимое ревью первого пользовательского сценария

Дата: 8 августа 2026 года.

## Вывод

Текущий интерфейс уже позволяет сохранить содержательные факты и не давит оценками, но новый пользователь не получает короткого пути к первому полезному результату. Приложение сначала показывает большую форму и объясняет разделы, а ценность недельной картины остаётся отложенной.

Главный подтверждённый дефект сценария: данные из «Журнала» не считаются достаточным основанием для показа недельной или месячной страницы. Пользователь может добавить реальный результат или событие, перейти в обзор и увидеть сообщение «пока нет записей». Это противоречит тексту интерфейса о том, что итоги и события входят в обзор периода.

Полный onboarding пока проектировать рано. Сначала нужно определить один первый результат и устранить разрыв между «Журналом» и обзором периода.

## Как проводилось ревью

- чистое локальное хранилище без демонстрационных данных;
- ширины 1280 и 390 пикселей;
- первый вход на «Сегодня»;
- объяснение «Как это работает»;
- переход в «Журнал» и добавление первого результата;
- переход в текущую неделю после записи в «Журнал»;
- проверка формы входа и регистрации по фактической разметке;
- сверка поведения с продуктовым контрактом и моделью покрытия данных.

Интервью и уведомления пользователям не проводились. Выводы ниже разделены на подтверждённые дефекты и продуктовые гипотезы.

## Что уже работает

- язык интерфейса спокойный и не превращает пропуск или тяжёлый день в провал;
- первый экран прямо сообщает, что заполнять всё не обязательно;
- ежедневные блоки можно настроить без удаления истории;
- работа не включена новому пользователю автоматически;
- календарь и возможность выбрать прошедший день теперь видимы;
- «Журнал» простыми словами различает итог, событие и наблюдение;
- мобильная навигация и сохранение остаются доступными на длинной форме;
- недельная аналитика честно отделяет заполненный день от записи без данных.

## Подтверждённые проблемы

### P1 — результат из «Журнала» исчезает из первого обзора

Сценарий воспроизведён на чистом хранилище:

1. открыть «Журнал»;
2. добавить первый итог;
3. перейти в текущую неделю;
4. увидеть «За эту неделю пока нет записей» без добавленного итога.

`WeekView` и `MonthView` выбирают пустое состояние только по `summary.coveredEntriesCount`. Итоги и события уже загружены для периода, но весь основной шаблон вместе с их карточками скрывается.

Минимальная граница исправления: различать «нет никаких данных периода» и «нет ежедневных записей, но есть данные Журнала». Во втором случае не нужно показывать пустые метрики дня, но нужно показать результаты и события периода с честным пояснением, что дневных данных для сравнений пока нет.

### P1 — до регистрации не объяснён результат продукта

`AuthGate` показывает название, поля аккаунта и код приглашения. Он не объясняет, кому предназначена «Траектория», какую проблему она решает и что пользователь получит после первых записей.

Для закрытой беты это частично компенсируется личным приглашением владельца, но интерфейс сам не отвечает на вопрос «зачем создавать аккаунт». Это совпадает с отдельной задачей о презентации до регистрации и не должно исправляться дополнительным текстом внутри формы входа без выбранной аудитории и обещания продукта.

### P2 — пустой день можно сохранить на десктопе

На чистой форме кнопка «Сохранить день» активна до любого ввода. Модель покрытия корректно не считает такую запись заполненным днём, однако сама запись переводит пользователя из состояния первого запуска в обычный режим. На мобильной ширине аналогичная кнопка до изменения формы скрыта, поэтому поведение различается между устройствами.

Нужно либо блокировать сохранение записи без единого явно отмеченного факта, либо дать отдельный осмысленный ответ «ничего не отмечаю». Автоматически превращать отсутствие ввода в заполненный день нельзя.

## Продуктовые гипотезы, а не подтверждённые дефекты

### Форма первого дня выглядит длиннее обещанного короткого ввода

На ширине 390 пикселей высота страницы составила около 3906 пикселей, а первое поле началось примерно на 593 пикселе. Заголовки групп улучшили структуру, но новый пользователь всё ещё видит много равноправных вариантов и не получает конкретного предложения, какие два-три ответа дадут первый полезный результат.

Это сильный риск трения, но по одному независимому просмотру нельзя утверждать, что пользователи массово не завершают запись. Решение должно исходить из заранее выбранного первого результата, а не из желания механически сократить форму.

### Объяснение продукта перегружено маршрутом по функциям

Диалог «Как это работает» последовательно объясняет пять частей приложения. Тексты точные, но пользователь должен удержать весь будущий процесс до первой записи. Сам диалог автоматически не открывается; его можно вызвать через кнопку помощи или из подсказки первой записи. Поле `introSeen` и режим `openForFirstVisit` существуют, но в основном сценарии не связаны.

Не следует просто включать автоматическое модальное окно. Более сильное решение — коротко показать обещание до регистрации, а внутри приложения давать следующий шаг в момент, когда он нужен.

### Первый полезный результат остаётся неопределённым

После одной записи приложение может показать факт сохранения и частичную недельную сводку, но полноценный обзор и решение доступны позже. Предложение восстановить предыдущие семь дней может ускорить ценность, однако оно создаст новый тип приблизительных данных и длинный onboarding, если сначала не определить ожидаемый результат.

Рабочая формулировка для следующего этапа: пользователь восстанавливает достаточно фактов, чтобы увидеть одну правдивую картину прошедшей недели и выбрать один ближайший фокус. Её ещё нужно проверить на совместимость с текущей моделью данных и правилами статистической честности.

## Рекомендуемая последовательность

1. Исправить отображение периода, когда есть только итоги или события из «Журнала».
2. Определить первую конкретную аудиторию и одно проверяемое обещание продукта.
3. Зафиксировать первый полезный результат до проектирования вопросов onboarding.
4. Спроектировать короткое восстановление недели как отдельный сценарий приблизительных данных, а не как семь обычных ежедневных форм.
5. Только после этого подготовить презентацию до регистрации и пошаговый onboarding.
6. Проверять новый сценарий автоматическими тестами и наблюдаемой воронкой внутри продукта; новые интервью сейчас не планировать.

## Чего пока не делать

- не включать автоматически существующий пятишаговый диалог;
- не скрывать большую часть формы только ради уменьшения высоты;
- не сохранять приблизительные ответы как точные ежедневные измерения;
- не строить onboarding до выбора первого результата;
- не добавлять новые обязательные поля;
- не считать этот аудит подтверждением целевой аудитории или спроса.

## Граница следующего этапа

Следующий продуктовый этап должен принять три решения:

1. для кого в первую очередь предназначена «Траектория»;
2. какое изменение состояния обещает продукт;
3. какой первый обзор доказывает пользователю эту ценность.

Только после этих решений можно безопасно переходить к реализации презентации, восстановления недели и onboarding.
