# Граница действующей закрытой беты

Закрытая бета началась 27 июля 2026 года; сейчас в ней пять реальных пользователей вместе с владельцем. Документ отделяет допустимую эксплуатацию этого доверенного круга от расширенной беты. Это инженерная граница риска, а не заключение о юридической достаточности: применимые требования зависят от владельца сервиса, стран участников и инфраструктуры.

Landing, годовая ретроспектива, конструктор блоков, остаточная полировка и web push не блокируют текущую доверенную бету.

## Что уже есть в репозитории

- вход и самостоятельная регистрация только по серверно проверяемому приглашению;
- подтверждение email, восстановление и смена пароля;
- RLS для пользовательского снимка и серверная функция полного удаления аккаунта;
- экспорт, очистка данных и локальная работа через IndexedDB;
- защита несохранённой ежедневной записи и контролируемая облачная сверка;
- production, staging, CI, PWA и проверяемые бюджеты сборки;
- встроенная форма обратной связи с авторизованной server-side доставкой.

## Немедленная проверка действующей беты

- [ ] Дать каждому участнику короткое понятное уведомление: какие данные сохраняются, где находится облачная копия, что это экспериментальный закрытый тест и как запросить удаление.
- [ ] Не приглашать несовершеннолетних до отдельной проверки.
- [ ] Настроить SMTP, Site URL, redirect URL и Auth rate limits в staging.
- [ ] Пройти одноразовым аккаунтом signup → подтверждение email → вход → запись → перезагрузка → экспорт → восстановление пароля → удаление аккаунта.
- [ ] После удаления подтвердить отсутствие Auth-пользователя и `trajectory_snapshots`, очистку локальной базы и невозможность использовать прежнюю сессию.
- [ ] Подтвердить RLS после последней миграции: один тестовый пользователь не видит и не изменяет снимок другого.
- [ ] Подтвердить отдельный email для обратной связи, server-side доставку и тестовое сообщение из того же окружения, которым пользуются участники.
- [ ] Указать контакт, по которому участник может сообщить о проблеме с данными или попросить удалить аккаунт.
- [ ] Включить безопасное наблюдение ошибок, получить тестовое событие и пройти учебный сценарий по [`INCIDENT_RESPONSE.md`](./INCIDENT_RESPONSE.md).

Для маленького доверенного круга допустимо временно оставить ручной резервный процесс: перед изменениями схемы делать проверенную копию staging и прямо предупредить участников, что сервис тестовый и им стоит периодически скачивать JSON-экспорт. Это осознанный риск потери данных, а не эквивалент автоматического backup.

## Что можно перенести только до расширения теста

- автоматический ежедневный backup, ротацию и регулярную учебную процедуру восстановления;
- полноценный публичный landing и отдельный центр справки;
- web push и другие каналы напоминаний;
- CAPTCHA, пока приглашение и rate limits реально сдерживают посторонние регистрации;
- расширенные cloud E2E, мониторинг и автоматизацию реагирования на инциденты;
- полный визуальный и архитектурный бэклог.

До приглашения незнакомых людей или заметного расширения круга снова обязательны юридическая проверка, опубликованная политика, проверка подрядчиков/регионов, автоматические backup и формальная процедура инцидентов из `docs/operations/DATA_GOVERNANCE.md`.

## Настройка встроенной формы

Vercel Preview для `develop` получает:

```text
VITE_FEEDBACK_ENABLED=true
VITE_ERROR_MONITORING_ENABLED=true
SUPABASE_URL=<staging Supabase URL>
SUPABASE_ANON_KEY=<staging anon key>
RESEND_API_KEY=<server-only secret>
FEEDBACK_TO_EMAIL=<отдельный адрес получателя>
FEEDBACK_FROM_EMAIL=Траектория <onboarding@resend.dev>
ERROR_TO_EMAIL=<отдельный адрес для технических событий или тот же получатель>
ERROR_FROM_EMAIL=Траектория <onboarding@resend.dev>
```

`FEEDBACK_TO_EMAIL`, `FEEDBACK_FROM_EMAIL`, `ERROR_TO_EMAIL`, `ERROR_FROM_EMAIL` и `RESEND_API_KEY` не являются `VITE_*` переменными и не попадают в браузер. Если отдельные `ERROR_*` не заданы, технические события используют адреса `FEEDBACK_*`. Самый короткий путь для доверенного теста: зарегистрировать Resend на новом адресе, указать этот же адрес в `FEEDBACK_TO_EMAIL` и использовать `onboarding@resend.dev` как отправителя — тестовый режим доставляет письма только владельцу Resend-аккаунта. Для другого получателя или расширения теста нужно подтвердить собственный домен и заменить адрес отправителя.

Форма содержит одно видимое поле. API принимает сообщение только от пользователя с действующей Supabase-сессией, ограничивает его 4000 символами и отправляет plain-text письмо. К письму автоматически добавляются email аккаунта и время; текст не сохраняется в IndexedDB, Supabase snapshot или logs приложения, но проходит через выбранного почтового провайдера и почтовый ящик. В интерфейсе явно указано, что нельзя отправлять пароли, код приглашения и содержимое личных записей.

## Решение по напоминаниям

Текущая закрытая бета продолжается без обещания push-напоминаний. Существующее напоминание о пропущенном вчера дне остаётся внутри ежедневного экрана. Спрос на системное уведомление и желаемое время проверяются в разговорах с участниками и через встроенную форму.

После подтверждения спроса Web Push реализуется отдельным release gate: явное включение пользователем, установленный PWA для iOS/iPadOS, серверное расписание по часовому поясу, защищённое хранение и удаление подписок, отсутствие содержимого дневника в сообщении, отписка в один шаг и сквозная проверка поддерживаемых платформ. Локальный `setTimeout` и Periodic Background Sync не используются как обещание ежедневной доставки.

## Как выпускать в `main` после staging

1. Довести изменения до зелёных `npm run audit:dependencies`, `npm run check` и `npm run test:e2e`.
2. Убедиться, что staging на `develop` проверен вручную на основном сценарии и на новом изменении.
3. Обновить `develop`, если понадобились правки после staging, и повторить проверку.
4. Создать release PR из `develop` в `main`.
5. После merge в `main` дождаться production deployment и ещё раз пройти короткий smoke-check.
6. Если production branch в Vercel закреплён за `main`, не переключать его на `develop` для обычного релиза.
