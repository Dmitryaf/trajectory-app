# Политика браузерных источников и заголовков

Статус: срез S2 опубликован на постоянном staging 12 сентября 2026 года и принят частично. Документ предназначен владельцу и разработчику для проверки staging; он не является публичной политикой безопасности.

## Инвентаризация источников

| Сценарий | Источник в браузере | Политика |
| --- | --- | --- |
| HTML, JavaScript, CSS, шрифты, иконки, manifest, service worker и чанки графиков | Текущий origin | `'self'` для соответствующей директивы |
| Supabase Auth, PostgREST и условная запись снимка | `https://<project-ref>.supabase.co` | `connect-src https://*.supabase.co` |
| Supabase Realtime | `wss://<project-ref>.supabase.co` | `connect-src wss://*.supabase.co` |
| `/api/feedback` и `/api/client-error` | Текущий origin | `connect-src 'self'` |
| Resend и серверная проверка Supabase Auth из Vercel Functions | Только сервер, не браузер | В браузерную CSP не входят |
| Ручной JSON-импорт и скачивание копии | Локальный файл или `blob:` без сетевой отправки | `blob:` разрешён только там, где он нужен браузеру |

В production-коде не обнаружены внешние CDN, web fonts, iframe, media-потоки или браузерные вызовы Resend. Новая внешняя зависимость должна обновить эту таблицу и contract-тест до поставки.

## Локально подготовленная политика

`vercel.json` назначает всем ответам:

- `Content-Security-Policy-Report-Only` с локальными ресурсами и Supabase HTTP/WebSocket;
- `X-Content-Type-Options: nosniff`;
- `X-Frame-Options: DENY`;
- `Referrer-Policy: strict-origin-when-cross-origin`;
- `Permissions-Policy: camera=(), geolocation=(), microphone=()`.

CSP пока не блокирует ресурсы. В ней намеренно нет `report-uri`, `report-to` и `Reporting-Endpoints`: отчёт о нарушении может содержать адрес ресурса или страницы, поэтому он не отправляется во внешнее хранилище. Нарушения проверяются только локально в DevTools на тестовом аккаунте без содержимого реальных записей.

`style-src` временно допускает `'unsafe-inline'`, потому что интерфейс использует вычисляемые inline-стили. Это известное ослабление, а не основание добавлять `'unsafe-eval'` или произвольные внешние origin.

## Staging-приёмка Report-Only

После публикации ветки в Preview:

1. Проверить заголовки `/`, `/settings`, `/assets/<реальный-js>` и `/api/client-error` через `curl -I`; API может вернуть ошибочный статус, но заголовки должны присутствовать.
2. В Chrome и Safari/WebKit открыть DevTools и пройти вход, восстановление сессии, загрузку Today, Week, Month и Trends.
3. Сохранить тестовую запись, дождаться записи снимка и Realtime-сверки второй сессии.
4. Проверить JSON-экспорт, импорт, скачивание конфликтной копии, feedback и тестовое техническое событие без личного текста.
5. Перезагрузить установленную PWA и убедиться, что service worker, manifest, иконки и отложенный чанк графиков загружаются.
6. Зафиксировать только директиву, тип и ожидаемый origin каждого нарушения. Полные URL, query-параметры, токены и содержимое записи в Issue или лог не копировать.

Срез принимается, если перечисленные сценарии работают, заголовок присутствует на HTML и статических ресурсах, а необъяснённых CSP-нарушений нет. Локальный `npm run test:e2e` не подтверждает Vercel-заголовки и не заменяет эту проверку.

### Проверенный branch Preview

12 сентября 2026 года Vercel успешно собрал commit `931b294` для ветки `fix/stabilize-mobile-webkit-e2e`.

- `/`, `/settings`, реальный JavaScript asset и `/api/client-error` получили все пять настроенных заголовков;
- HTML и маршрут настроек вернули `200`, asset сохранил immutable-cache, а GET к POST-only API ожидаемо вернул `405`;
- публичный fail-closed экран загрузился без сетевых отказов в Chromium и WebKit;
- Chromium не сообщил CSP-нарушений;
- WebKit сообщил о том, что `frame-ancestors` не применяется в Report-Only и политика без reporting endpoint не отправляет отчёты;
- остальные WebKit-предупреждения относились только к script/iframe с origin `vercel.live`, внедрённым Preview Toolbar, а не к ресурсам приложения. Этот origin не добавляется в production-политику.

Этот branch Preview не получил конфигурацию Supabase и правильно закрылся нейтральным экраном. Поэтому проверка подтверждает доставку заголовков и публичную fail-closed границу, но не Auth, Realtime, API с сессией, установленную PWA или конфликт двух устройств. Эти пункты остаются для постоянного staging на `develop`.

### Проверенный постоянный staging

12 сентября 2026 года PR #82 объединён в `develop` как commit `82ad7db`. Vercel опубликовал этот commit на постоянном staging, а post-merge CI завершил `npm run check` и браузерный набор с результатом 114 passed, 1 expected skipped.

Без пользовательской сессии подтверждено:

- `/`, `/week`, `/month`, `/trends`, `/more`, `/results`, `/events`, `/settings` и `/password-reset` вернули HTML `200`;
- реальный JavaScript asset, manifest, service worker и три manifest-иконки вернули `200` с ожидаемым MIME, а заведомо отсутствующий asset — `404`;
- HTML, JavaScript и POST-only `/api/client-error` получили все пять настроенных заголовков; GET к API ожидаемо вернул `405`;
- свежие Chromium- и WebKit-сессии загрузили собственный экран входа без сетевых отказов; Chromium не сообщил CSP-нарушений, а WebKit сообщил только ожидаемое ограничение `frame-ancestors` в Report-Only и предупреждения Preview Toolbar с origin `vercel.live`;
- анонимный запрос к `trajectory_snapshots` вернул пустой список, оба server-side API без сессии вернули `401`, а с чужим Origin — `403`;
- в Chromium service worker взял страницу под контроль, и оболочка продолжила загружаться после перехода браузера offline.

Проверка не создавала аккаунтов или пользовательских данных. В рабочем окружении агента нет staging-учётной записи или кода приглашения, поэтому пока не подтверждены вход и восстановление сессии, запись и Realtime-сверка, явный выбор при конфликте двух устройств, API с действующей сессией, установленная PWA, отложенный чанк графиков, email-восстановление и удаление аккаунта. Эти пункты остаются в Issue #65 и staging-приёмке S1/S2; CSP остаётся в Report-Only.

## Решение об enforcement

`Content-Security-Policy` вместо Report-Only включается отдельным изменением только после staging-приёмки. Перед этим:

- каждый разрешённый origin связывается с действующим сценарием;
- проверяются Chrome, Safari и установленная PWA;
- неизвестный источник не разрешается маской ради исчезновения предупреждения;
- отдельно решается сокращение `'unsafe-inline'`;
- не добавляется сбор CSP-отчётов без модели минимизации, доступа и срока хранения.

Если staging обнаружит необходимый источник, сначала обновляются инвентаризация и contract-тест, затем повторяется вся профильная проверка.
