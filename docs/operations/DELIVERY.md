# Поставка и допуск к выпуску

Процедура для разработчика и оператора. Обновляется при изменении CI, окружений или способа выпуска. Это единый release gate; результаты конкретного прогона и решение владельца фиксируются в Issue/PR, а успешные jobs — в CI.

## Ветки и окружения

- `develop` — общая версия следующего релиза и постоянный staging.
- `main` — проверенные production-релизы.
- `feature/*`, `fix/*`, `docs/*`, `refactor/*`, `ci/*` — короткие ветки одной задачи.

Обычный путь: короткая ветка → PR в `develop` → Preview → постоянный staging → release PR в `main` → production.

Task PR объединяется через **Squash and merge**. Release PR `develop → main` — через **Create a merge commit**, чтобы сохранить ancestry и не повторять уже выпущенные изменения. Hotfix создаётся от `main`, проверяется отдельно и после production возвращается в `develop`.

После проверенного выпуска допустим именованный prerelease `vX.Y.Z-beta.N`. До следующего тега сверяются существующие releases, совместимость и точный target commit. Несовместимое поведение или миграция требуют отдельного решения о базовой версии.

## Настройка сред

1. В GitHub для `develop` и `main` настроить защиту от удаления и force-push, обязательный PR, успешный `test-and-build`, актуальность ветки и разрешённые обсуждения. Обход — только для явно согласованного аварийного восстановления. Второе одобрение не требуется при одном разработчике.
2. В Vercel Production Branch Tracking закрепить за `main`; короткие ветки используют Preview. Постоянный staging — Preview ветки `develop`: [адрес стенда](https://trajectory-app-git-develop-trajectory3.vercel.app/).
3. Для `develop` назначить отдельные branch-scoped Preview-переменные и staging Supabase. Production-ключи и реальные записи участников в Preview не копируются.
4. Preview требует авторизации и остаётся `noindex`. Ветка без backend-переменных должна закрываться нейтральным экраном. Проверить, что защита самого Preview не ломает переходы из писем Auth.
5. Supabase, SMTP, серверное приглашение, rate limits и почтовые API настроить по [BACKEND_AUTH_CI](BACKEND_AUTH_CI.md).

Эти параметры проверяются в GitHub/Vercel/Supabase: наличие инструкции не означает, что внешняя настройка уже выполнена. Публичность репозитория сама по себе не включает branch protection.

## Автоматическая граница

[ci.yml](../../.github/workflows/ci.yml) запускается для PR и push в `develop`/`main`. Версия Node задаётся [.nvmrc](../../.nvmrc), зависимости — lock-файлом.

CI устанавливает зависимости через `npm ci`, выполняет `audit:dependencies`, `check` и `test:e2e:ci`. Точный состав команд — в [package.json](../../package.json). Браузерная матрица включает Chromium, WebKit и Mobile Safari; flaky-сценарий блокирует CI. Эмуляция не подтверждает физическое устройство.

Перед поставкой проверяется успешный job **для точного commit**, а не только общий зелёный статус или готовность Vercel Preview. Ошибки зависимостей высокой/критической важности блокируют поставку; меньшие оцениваются по достижимости и риску.

Локальная граница по типу изменения — в [PROJECT_RULES](../../.ai-rules/PROJECT_RULES.md). Husky `pre-commit` запускает полный `check`, кроме staged-путей только в `docs/` и корневых `*.md`, для которых выполняется diff-check. Markdown в `.ai-rules/` и `.github/` сейчас не входит в это исключение hook. `commit-msg` проверяет Conventional Commits; сообщения пишутся на английском.

## Gate перед расширением аудитории и release PR

- [ ] Определены владелец запуска, аудитория и поддерживаемые платформы; открытые блокеры проверены в Project/Issues.
- [ ] Выполнены требования [DATA_GOVERNANCE](DATA_GOVERNANCE.md): публичная политика, применимые требования и возрастная граница, контакт, подрядчики/регионы, подтверждённые сроки хранения и удаления.
- [ ] Автоматический зашифрованный backup вне основного хранилища, ротация и восстановление в отдельном контуре проверены. Экспорт пользователя не подменяет резервирование сервиса.
- [ ] CI точного `develop` завершён успешно; миграции имеют проверенную совместимость и безопасный откат либо согласованный путь вперёд.
- [ ] Одноразовыми аккаунтами пройдены регистрация/письмо/вход, локальная запись, sync, экспорт/импорт, восстановление пароля, удаление и проверка прежней сессии.
- [ ] Проверены RLS двух пользователей и конфликт двух устройств, включая edit/delete, offline/reconnect, отмену и повтор явного выбора.
- [ ] Пройдены [MANUAL_REGRESSION](MANUAL_REGRESSION.md), физическая матрица [PWA_INSTALLATION](PWA_INSTALLATION.md), доступность критического пути и измерение производительности.
- [ ] Заголовки и действующие Auth/Realtime/API/графики/PWA приняты по [SECURITY_HEADERS](SECURITY_HEADERS.md). Режим CSP назван явно.
- [ ] Обратная связь и безопасное событие реально доставлены из целевой среды; учебная реакция пройдена по [INCIDENT_RESPONSE](INCIDENT_RESPONSE.md).
- [ ] Назначены текущий и проверенный deployment для отката; выполнена репетиция без изменения production.
- [ ] В Issue/PR сохранены commit, окружение, доказательства и ограничения без личных данных. Владелец явно решил: выпускать, отложить или сузить границу.

Gate не открывает регистрацию автоматически. Изменение серверного режима допуска и расширение аудитории — отдельное решение; UI-флаг не защищает signup.

## SPA и PWA при поставке

Для изменения маршрутов, Vite/PWA, service worker, Vercel или сборки:

1. Проверить прямое открытие всех маршрутов из `src/main.ts`.
2. Проверить `200` и корректный MIME для JavaScript/CSS из HTML, manifest, service worker и иконок.
3. Отсутствующий `/assets/*.js` должен вернуть `404`, не `index.html`. SPA/navigation fallback не применяется к `/api` и `/assets`.
4. HTML и service worker перепроверяются; ресурсы с хешем могут иметь immutable-cache.
5. Проверить свежую сессию и открытую вкладку при обновлении. Старый dynamic import не оставляет пустой экран; локальный черновик сохраняется.

Физические install/offline/session/update-сценарии выполняются только по [PWA_INSTALLATION](PWA_INSTALLATION.md).

## Production и откат

После разрешённого merge release PR дождаться успешного CI и deployment точного `main`. Повторить короткий smoke: вход, прямой маршрут, «Сегодня», сохранение, перезагрузка, sync и экспорт; проверить API и заголовки. Не переключать production branch на `develop`.

При проблеме остановить дальнейший выпуск и использовать заранее проверенный deployment. Откат frontend не откатывает IndexedDB, облачную схему и service worker на каждом устройстве: совместимость с уже записанными данными проверяется до переключения. Повреждённые данные сначала восстанавливаются в отдельном контуре по [DATA_GOVERNANCE](DATA_GOVERNANCE.md). При инциденте применяется [INCIDENT_RESPONSE](INCIDENT_RESPONSE.md).
