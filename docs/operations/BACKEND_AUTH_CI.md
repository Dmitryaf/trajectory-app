# Настройка backend и авторизации

Процедура настройки конкретного окружения для оператора. Пересматривается при изменении переменных, миграций или серверных обработчиков. Устройство синхронизации описывает [ARCHITECTURE](../development/ARCHITECTURE.md), ветки и приёмку — [DELIVERY](DELIVERY.md).

## Supabase

1. Создать отдельный проект для окружения. Оставить signup выключенным.
2. Применить все миграции из [supabase/migrations](../../supabase/migrations/) в порядке имён.
3. Настроить email-подтверждение, Site URL и разрешённые redirect URL, включая `/password-reset`. Подготовить тестовый аккаунт без реальных записей.
4. Назначить Vercel frontend-переменные проекта:

```text
VITE_SUPABASE_URL=<URL этого Supabase>
VITE_SUPABASE_ANON_KEY=<публичный anon/publishable key>
VITE_REQUIRE_AUTH=true
VITE_ENABLE_BETA_SIGNUP=false
```

Публичный ключ допустим в браузере только при работающих RLS. `service_role` и административные ключи никогда не помещаются в `VITE_*`. Доступ к `trajectory_snapshots` проверяется двумя пользователями и анонимным запросом после применения миграций.

## Регистрация по приглашению

Действующий серверный механизм — `Before User Created` hook с кодом и лимитом. Frontend-флаг лишь показывает форму. Настраивать сначала staging:

1. Оставить `Allow new users to sign up` выключенным.
2. Убедиться, что применена миграция beta signup gate.
3. Через защищённый SQL Editor задать отдельный код и лимит:

```sql
select private.configure_beta_signup('replace-with-a-long-random-code', 15, true);
```

Это пример. Реальный код не сохраняется в репозиторий, логи, screenshots или переменные frontend. Настройка сбрасывает счётчик попыток регистрации; не вызывать её как безвредную повторную проверку.

4. Подключить `public.hook_require_beta_invite` в Authentication Hooks → Before User Created.
5. Развернуть функцию удаления в том же Supabase:

```text
npx supabase functions deploy delete-account --project-ref <project-ref>
```

Сохранить обязательную JWT-проверку и серверную проверку пользователя внутри обработчика. Не отключать их ради успешного запроса.

6. Настроить SMTP, отправителя, подтверждение email и Auth rate limits. CAPTCHA включается только при совместимом клиентском сценарии.
7. Включить signup в Supabase, затем `VITE_ENABLE_BETA_SIGNUP=true` только в соответствующем Vercel environment и пересобрать его.
8. Проверить неверный код, положительную регистрацию, получение письма, вход, recovery, RLS и полное удаление по [MANUAL_REGRESSION](MANUAL_REGRESSION.md).

Hook отклоняет запрос до создания пользователя; trigger убирает приглашение из сохранённых metadata. Счётчик signup не является числом подтверждённых или активных пользователей.

Для остановки набора сначала отключить его на сервере:

```sql
select private.configure_beta_signup('', 15, false);
```

Затем выключить Supabase signup и frontend-флаг при следующем deployment. Production настраивается отдельно с другим кодом. Неограниченная регистрация не включается простым удалением hook или сменой UI-флага без отдельного решения о допуске.

## Обратная связь и технические ошибки

Оба API размещены в Vercel. Для выбранного окружения задаются:

```text
VITE_FEEDBACK_ENABLED=true
VITE_ERROR_MONITORING_ENABLED=true
SUPABASE_URL=<URL того же проекта>
SUPABASE_ANON_KEY=<публичный ключ того же проекта>
RESEND_API_KEY=<server-only secret>
FEEDBACK_TO_EMAIL=<получатель обратной связи>
FEEDBACK_FROM_EMAIL=<подтверждённый отправитель>
ERROR_TO_EMAIL=<получатель технических событий>
ERROR_FROM_EMAIL=<подтверждённый отправитель>
```

`RESEND_API_KEY` и адреса не являются `VITE_*` и остаются на сервере. Без отдельных `ERROR_*` обработчик использует `FEEDBACK_*`. Проверить ограничения отправителя и получателя в реальном почтовом аккаунте; тестовый режим провайдера не доказывает доставку другим адресатам.

После изменения переменных пересобрать нужное окружение. Под тестовой сессией отправить нейтральное сообщение и техническое событие, подтвердить получение, затем проверить отказ без сессии и с чужим Origin.

`/api/feedback` принимает сообщение до 4000 символов и отправляет plain-text письмо с email аккаунта и временем. Оно не записывается приложением в IndexedDB или snapshot, но хранится у почтового провайдера и получателя. Интерфейс предупреждает не отправлять пароли, приглашения и содержимое дневника. Контракт `/api/client-error` и учебная проверка — в [INCIDENT_RESPONSE](INCIDENT_RESPONSE.md).

## Проверка настройки

В целевой среде должны совпадать frontend и server-side Supabase URL, ключи, deployment функции и адреса переходов Auth. Без обязательной backend-конфигурации приложение должно закрываться безопасным экраном. Наличие переменных и deployment не считается проверкой SMTP, RLS или удаления.

Серверные секреты, реальные учётные данные и команды с ними не включаются в публичные отчёты. Общая приёмка после setup выполняется по [DELIVERY](DELIVERY.md).
