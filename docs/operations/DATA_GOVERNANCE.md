# Данные и допуск внешних пользователей

Этот документ задаёт внутренний технический контур. Он не заменяет публичную политику конфиденциальности и юридическую проверку для выбранных стран запуска.

## Почему данные требуют повышенной защиты

Приложение может хранить email, сон, вес, питание, самочувствие, рабочие действия, события и свободный текст. Даже без медицинских выводов такой набор раскрывает личный распорядок и состояние человека. Содержимое дневника не должно попадать в логи, аналитику посещений или демонстрационные снимки.

## Карта данных

| Данные | Цель | Где находятся сейчас |
| --- | --- | --- |
| Email и данные входа | Доступ к облачной копии | Supabase Auth |
| Записи, обзоры, итоги, события и настройки | Основной сценарий и синхронизация | IndexedDB и один JSONB-снимок Supabase |
| Несохранённый черновик дневной записи | Защита введённых данных до явного сохранения дня | Только IndexedDB текущего браузера; не входит в облако и JSON-экспорт |
| Состояние синхронизации | Предотвращение потери локальных изменений | localStorage без содержимого дневника |
| События первого использования | Проверка прохождения первого сценария | localStorage: только название события и время, без содержимого записей; не входит в облако и экспорт |
| Ручной JSON-экспорт | Резервная копия и переносимость | Файл, который сохраняет пользователь |
| Промпт для внешней нейросети | Только ручной анализ по решению пользователя | Буфер обмена; приложение само ничего не отправляет |

До запуска нужно отдельно описать технические логи хостинга, Auth и базы: состав, регион, доступ и срок хранения.

## Обязательные решения до приглашения пользователей

1. Зафиксировать страны запуска, владельца сервиса и контакт для запросов о данных.
2. Получить юридическую проверку применимых требований, включая локализацию и трансграничную передачу.
3. Опубликовать понятную политику: категории данных, цели, правовое основание обработки, подрядчики, регионы, сроки, права пользователя и дата версии. Хранить подтверждение принятой версии документов; отдельное согласие запрашивать там, где именно оно является выбранным или обязательным основанием.
4. Определить возрастное ограничение. До отдельной проверки не запускать продукт для несовершеннолетних.
5. Заключить или принять необходимые соглашения с обработчиками данных и вести список их субподрядчиков.
6. Утвердить сроки хранения и подтвердить их реальной конфигурацией инфраструктуры.
7. Подготовить порядок реакции на инцидент: обнаружение, ограничение, оценка, уведомление и разбор причины.

## Целевая политика хранения

Это продуктовые ориентиры для последующей юридической проверки:

- активные данные хранятся, пока аккаунт используется и они нужны для долгосрочных обзоров;
- после 24 месяцев без входа пользователь получает предупреждение, после которого аккаунт может быть удалён;
- удаление аккаунта немедленно блокирует вход и удаляет основную облачную копию не позднее 24 часов;
- удалённые данные исчезают из резервных копий по мере их ротации, целевой предел — 30 дней;
- прикладные логи без содержимого дневника хранятся не более 30 дней, события безопасности — не более 90 дней;
- резервные копии шифруются, находятся вне основного сервера и регулярно удаляются по расписанию.

Если инфраструктура не может выполнить заявленный срок, публичная политика не должна обещать его.

## Функции, необходимые до запуска

- экспорт всех данных в читаемом и переносимом формате;
- удаление отдельных записей;
- отдельное удаление всего содержимого без удаления аккаунта;
- удаление аккаунта с повторным подтверждением личности;
- удаление строки `trajectory_snapshots`, пользователя Auth, локальной базы, sync-метаданных и активных сессий;
- понятный статус завершения или ошибки удаления;
- серверная операция удаления Auth без административного ключа в браузере.

Команда «Удалить все данные» по-прежнему оставляет аккаунт и синхронизирует пустой снимок. Отдельная команда «Удалить аккаунт» вызывает защищённую серверную функцию: она повторно проверяет токен текущего пользователя, удаляет этого Auth-пользователя и каскадно его облачный снимок. После серверного успеха браузер очищает локальную базу, sync-метаданные и сессию. Если IndexedDB очистить не удалось, приложение скрывает данные из памяти и прямо сообщает, что аккаунт и облачная копия уже удалены, а данные сайта нужно очистить в настройках браузера. Реализация считается готовой к внешнему тесту только после deployment и сквозной проверки на staging.

## Граница закрытого теста

Текущая модель хранения не использует сквозное шифрование. Политики доступа отделяют облачные снимки участников друг от друга, но владелец инфраструктуры сохраняет техническую возможность административного доступа к хранилищу. Нельзя обещать участникам, что владелец не способен прочитать их данные.

Если до полного внешнего запуска приглашается небольшая группа знакомых, это остаётся закрытым тестом на доверии. Дружеские отношения не отменяют статус внешнего пользователя и применимые обязанности. Инженерный минимум для такого теста зафиксирован в `docs/operations/BETA_RELEASE.md`:

- участник может создать аккаунт сам только по серверно проверяемому приглашению; неограниченная публичная регистрация выключена;
- техническая граница доступа учитывается во внутренних процедурах и будущей политике обработки данных, но не выносится отдельным техническим пояснением на экран входа;
- приложение не отправляет содержимое дневника во внешнюю аналитику или нейросеть автоматически;
- участник может самостоятельно скачать экспорт, очистить содержимое или полностью удалить свой аккаунт; перед приглашениями этот сценарий должен быть развёрнут и проверен на staging;
- участник заранее получает простое уведомление об экспериментальном статусе, облачном хранении, риске потери данных, экспорте и способе запросить удаление;
- расширение за пределы нескольких доверенных знакомых возвращает все обязательные решения из release gate ниже.

Шифрование содержимого на стороне клиента не входит в текущий план. Если модель доверия перестанет подходить, решение пересматривается отдельно вместе с восстановлением доступа, синхронизацией и резервными копиями, а не добавляется частичной надстройкой.

## Резервные копии и восстановление

- для production выполнять ежедневный логический dump;
- хранить минимум одну копию в другом провайдере или хранилище;
- не помещать незашифрованные пользовательские данные в GitHub artifacts;
- ежемесячно проверять восстановление на отдельном staging;
- фиксировать время копии, результат проверки и ожидаемую потерю данных;
- перед изменением схемы создавать дополнительную проверенную копию.

Целевые показатели для раннего запуска: потеря не более 24 часов данных и восстановление основной функции не более чем за 4 часа. Они считаются подтверждёнными только после учебного восстановления.

## Release gate расширенной внешней беты

Нельзя приглашать незнакомых участников, расширять тест или представлять его как готовый публичный сервис, пока не выполнены все пункты:

- [ ] определены юрисдикция и публичные документы;
- [ ] проверены подрядчики, регионы и трансграничная передача;
- [ ] работает полное удаление аккаунта;
- [ ] ежедневный backup и ротация выполняются автоматически;
- [ ] восстановление проверено на staging;
- [ ] содержимое дневника отсутствует в логах и телеметрии;
- [ ] RLS и изоляция пользователей проверены после последней схемной миграции;
- [ ] есть контакт и процедура обработки запроса пользователя или инцидента.

## Базовые источники для юридической проверки

- принципы GDPR: законность, прозрачность, ограничение цели, минимизация, точность, ограничение хранения и безопасность — https://commission.europa.eu/law/law-topic/data-protection/reform/what-does-general-data-protection-regulation-gdpr-govern_en;
- обязанности оператора и порядок уведомления Роскомнадзора — https://82.rkn.gov.ru/directions/pers/p15375/;
- резервное копирование Supabase и рекомендация внешних CLI-копий для Free plan — https://supabase.com/docs/guides/platform/backups.

Ссылки задают отправную точку, но не определяют автоматически применимое право для конкретного владельца, страны пользователей и места размещения сервера.
