# Переносимая инфраструктура и собственный домен

Цель — не переехать как можно раньше, а сохранить возможность сменить провайдера без потери данных и длительной недоступности.

## Рекомендуемый путь

1. Оставить статический frontend на Vercel, пока проект остаётся личным и некоммерческим.
2. Купить домен после выбора устойчивого названия и использовать его как постоянную пользовательскую точку входа.
3. Подготовить backend к переносу независимо от frontend.
4. Сначала провести полный перенос на staging, затем перенести production с коротким окном без записи.
5. Переносить frontend с Vercel на VPS только при реальной экономии, ограничении тарифа или требовании контроля.

Свой домен можно подключить к Vercel без переноса приложения. Пользовательский адрес останется тем же, даже если позднее DNS будет направлен на собственный сервер.

## Имена сред

- `app.example.ru` — production frontend;
- `staging.example.ru` — staging frontend;
- `api.example.ru` — production Auth и API;
- `api-staging.example.ru` — staging Auth и API.

Frontend не должен хранить адрес провайдера в продуктовой логике: окружение передаёт только публичный URL backend и публичный ключ. Redirect URL Auth задаются через постоянные домены.

## Границы приложения

Сейчас перенос упрощает один JSONB-снимок на пользователя, но Auth и доступ к таблице вызываются напрямую через Supabase SDK. До миграции нужно:

- выделить интерфейс `CloudBackend` для входа, сессии, чтения, записи и удаления аккаунта;
- оставить Supabase одной реализацией этого интерфейса;
- хранить SQL-миграции единственным источником схемы;
- не использовать platform-only функции без плана замены;
- вынести административные операции в доверенный server-side слой.

## Варианты размещения

### Гибридный — предпочтительный первый этап

Frontend остаётся на Vercel с собственным доменом, Supabase переносится на VPS. Это уменьшает объём одного переключения и сохраняет простую доставку статического PWA.

### Полный VPS

Reverse proxy раздаёт frontend и TLS, Supabase запускается через Docker Compose. Этот вариант снижает прямые платежи провайдерам, но владелец отвечает за обновления, firewall, секреты, мониторинг, Postgres, backup и восстановление.

Для раннего небольшого запуска production и staging могут находиться на одном VPS только при раздельных Compose-проектах, базах, ролях, сетях, volumes и секретах. Это не даёт отказоустойчивости: backup обязан находиться вне VPS. При росте production и staging разводятся по серверам.

## Подготовка VPS

- поддерживаемая LTS-система и автоматические security updates;
- закрытые наружу Postgres, Studio и внутренние сервисы;
- наружу доступны только `80/443`, SSH ограничен ключами и firewall;
- TLS, HSTS после проверки, rate limiting для Auth;
- секреты находятся вне репозитория и не передаются frontend;
- health checks, мониторинг диска, памяти, контейнеров и срока последнего backup;
- автоматический restart и проверяемая процедура обновления;
- off-site backup с шифрованием и ротацией.

## Репетиция переноса

1. Поднять новый self-hosted staging нужной версии.
2. Экспортировать роли, схему и данные через `supabase db dump` отдельными файлами.
3. Восстановить их в тестовую среду и применить недостающие конфигурационные параметры.
4. Проверить пользователей Auth, RLS, вход, запись, синхронизацию, экспорт и удаление аккаунта.
5. Учесть, что старые JWT станут недействительными и пользователям понадобится повторный вход.
6. Проверить redirect URL и отправку писем Auth с новых доменов.
7. Выполнить тестовое восстановление из off-site backup и измерить время.

## Production cutover

1. За 24–48 часов уменьшить TTL записей `api`.
2. Объявить короткое окно обслуживания и остановить новые записи.
3. Сделать финальные dumps ролей, схемы и данных, проверить контрольные суммы.
4. Восстановить production, сравнить число пользователей и снимков.
5. Выполнить автоматический smoke и ручной тест отдельным пользователем.
6. Переключить DNS `api`, обновить frontend environment и Auth redirects.
7. Проверить свежий вход, повторный вход, запись и чтение на реальном домене.
8. Оставить старую систему в режиме только чтения на ограниченное окно отката.
9. После сверки и окончания окна удалить старые данные по зафиксированной процедуре.

## Условия отката

Переключение отменяется, если не работает Auth, нарушена изоляция RLS, расходятся число снимков или контрольные суммы, backup не восстанавливается либо основной сценарий не проходит smoke. Обратный DNS переключается на старый backend, а записи в новой системе сохраняются для последующей сверки и не затирают старую базу автоматически.

## Что не делать заранее

- не переписывать рабочую синхронизацию только ради гипотетического VPS;
- не размещать production без автоматического off-site backup;
- не считать staging отдельным, если он использует production-базу или секреты;
- не переключать frontend, Auth, базу и DNS одним непроверенным действием;
- не обещать SLA, RPO или сроки удаления до проверочного восстановления.
